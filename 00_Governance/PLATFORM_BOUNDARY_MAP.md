# PLATFORM_BOUNDARY_MAP

## Purpose

This document defines the official institutional boundaries within the Oak Ridge Management ecosystem.

It exists to prevent:

- ownership ambiguity
- narrative drift
- platform blur
- deployment confusion
- repository consolidation errors
- misclassification of products, standards, and execution entities

This is a governance and institutional-boundary document.

It is not:

- a software architecture spec
- a repo migration checklist
- a UI/UX standard
- a deployment runbook

Its function is to establish the official relationship boundaries between:

- Oak Ridge Management
- CEH Standard
- CEH Infrastructure Index
- DGE&I

All future website restructuring, repo consolidation, public narrative, and deployment topology decisions must conform to this document.

---

# 1. Entity Definitions

## Oak Ridge Management

Oak Ridge Management, or ORM, is the parent platform, governance, and ownership layer of the ecosystem.

ORM functions as:

- control layer
- governance authority
- intellectual property owner
- narrative authority
- platform architect
- standards steward
- deployment authority for ORM-controlled properties

ORM is the institutional home under which the broader platform is organized.

## CEH Standard

CEH Standard is the standards and methodology layer.

It functions as:

- the compute-energy measurement standard
- the benchmarking and certification logic layer
- the methodology and versioning framework
- the standards publication layer

CEH Standard is ORM-owned intellectual property and must remain institutionally distinct from execution and capital formation activities.

## CEH Infrastructure Index

CEH Infrastructure Index is the product and intelligence layer built around CEH methodologies.

It functions as:

- analytical product
- market intelligence platform
- benchmarking and ranking product
- capital-markets information layer
- CEH-applied productization layer

The Index is not the standard itself. It is the commercial and analytical application layer built on top of CEH logic.

## DGE&I

DGE&I is the execution, deployment, and reference implementation layer.

It functions as:

- infrastructure execution partner
- deployment/reference implementation
- capital and project execution vehicle
- real-world operating environment for infrastructure deployment

DGE&I is not the governance authority and is not the owner of CEH.

# 2. Ownership Relationships

## Parent Ownership Structure

The official hierarchy is:

1. Oak Ridge Management
2. CEH Standard
3. CEH Infrastructure Index
4. DGE&I

## Formal Ownership Rules

ORM owns:

- CEH Standard
- CEH Infrastructure Index
- ORM narrative system
- ORM governance system
- platform-level digital architecture
- official brand hierarchy
- canonical ecosystem positioning

CEH Standard does not own ORM.

CEH Infrastructure Index does not own CEH Standard.

DGE&I does not own CEH Standard, CEH Infrastructure Index, or ORM.

DGE&I may use, reference, apply, or be evaluated through CEH-related systems, but such usage does not imply ownership.

## Ownership Interpretation Rule

If any file, page, repo, design, partner document, or deployment implies that DGE&I is the parent entity, that implication is incorrect.

If any file, page, repo, design, partner document, or deployment implies that CEH exists outside ORM ownership, that implication is incorrect.

# 4. Narrative Boundaries

## Official Narrative Ladder

All public-facing and internal-facing platform communications must preserve this narrative order:

1. ORM = parent control layer
2. CEH Standard = methodology and standards layer
3. CEH Infrastructure Index = analytical/product layer
4. DGE&I = execution/reference implementation layer

## Narrative Rules

ORM narrative should emphasize:

- institutional control
- ownership
- standards stewardship
- governance
- platform architecture
- long-term system design

CEH Standard narrative should emphasize:

- independent methodology
- benchmarking logic
- versioned standard
- certification framework
- reproducibility
- institutional rigor

CEH Infrastructure Index narrative should emphasize:

- intelligence
- rankings
- market insight
- productized analytics
- CEH-applied evaluation
- institutional subscribers and counterparties

DGE&I narrative should emphasize:

- deployment
- execution
- implementation
- infrastructure delivery
- real-world application
- reference implementation

## Narrative Separation Rule

DGE&I must never be described as the institutional home of CEH.

CEH Infrastructure Index must never be described as the standard itself.

CEH Standard must never be described as a capital vehicle.

ORM must not be framed as subordinate to DGE&I, nor collapsed into DGE&I operating language.

# 5. Deployment Boundaries

## Deployment Principle

Institutional boundaries must be reflected in deployment boundaries.

Different entities may share governance, but they should not share uncontrolled public deployment surfaces.

## Deployment Roles by Entity

ORM deployments should contain:

- parent platform narrative
- ownership language
- hierarchy explanation
- high-level ecosystem orientation
- links downward to CEH, CEH Index, and DGE&I

CEH Standard deployments should contain:

- methodology
- standard definitions
- versioning
- benchmarking logic
- certification framing

CEH Infrastructure Index deployments should contain:

- rankings
- intelligence
- capital series
- access requests
- index-specific methodology

DGE&I deployments should contain:

- execution materials
- project/deployment reference content
- investor or deployment-specific content
- implementation narratives

## Deployment Boundary Rule

A public deployment should not simultaneously function as:

- ORM parent site
- CEH Standard canonical site
- CEH Index canonical site
- DGE&I execution site

unless the deployment is explicitly transitional and documented as such.

# 6. Domain Ownership Boundaries

## Canonical Domain Principle

Each major entity layer should have one clearly defined canonical public home.

## Domain Boundary Model

ORM canonical domain should represent:

- parent platform
- ownership hierarchy
- ecosystem map
- institutional authority

CEH Standard canonical domain should represent:

- the standard
- methodology
- official publication and certification logic

CEH Infrastructure Index canonical domain should represent:

- the product
- intelligence outputs
- ranking and access model

DGE&I domain or portal should represent:

- execution layer
- reference implementation
- infrastructure and capital execution materials

## Domain Rule

A domain must not imply one entity while canonically serving another.

Examples of prohibited ambiguity:

- CEH Infrastructure Index canonical URLs pointing to CEH Standard paths without formal canonical policy
- DGE&I portals framed as the ecosystem parent
- CEH content hosted under DGE&I structures in a way that implies DGE&I ownership

## Domain Ownership Rule

Domain ownership and canonical declaration must follow the institutional hierarchy, not historical convenience.

# 7. Shared Services Boundaries

## Shared Services Principle

Shared services may be centralized, but shared services do not eliminate entity boundaries.

## What May Be Shared

The following may be shared across the ecosystem if governance approves:

- design tokens
- typography rules
- navigation frameworks
- footer systems
- legal disclosures
- analytics conventions
- form infrastructure
- component primitives
- shared asset storage
- deployment tooling
- branch governance
- authentication infrastructure
- internal operational tooling

## What Must Not Be Collapsed Into Shared Services

The following must remain entity-specific unless formally approved otherwise:

- ownership language
- product identity
- standards language
- DGE&I execution narrative
- capital-market positioning
- canonical “about” framing
- certification vs ranking distinctions
- entity-specific disclosures

## Shared Services Rule

Shared services support clarity.
They must not be used to flatten institutional differences.

# 8. Future Monorepo Implications

## Monorepo Principle

A future ORM monorepo may centralize control, but must not erase institutional boundaries.

## What a Monorepo May Centralize

A monorepo may centralize:

- governance files
- shared assets
- deployment rules
- shared styles
- base components
- operational tooling
- branch/deploy workflows
- internal documentation
- migration inventories

## What a Monorepo Must Preserve

A monorepo must preserve:

- ORM as parent layer
- CEH Standard as methodology layer
- CEH Infrastructure Index as product layer
- DGE&I as execution/reference layer
- separate deployment targets
- separate canonical domains
- separate narrative boundaries
- separate ownership framing

## Monorepo Rule

Technical consolidation must follow institutional clarity.

If boundaries are unclear, consolidation must wait.

The monorepo is a control structure, not a justification for narrative blending.

# 9. Explicit Anti-Blur Rules

The following rules are mandatory.

## Anti-Blur Rule 1
DGE&I must never be presented as the parent ecosystem.

## Anti-Blur Rule 2
CEH Standard must always be represented as ORM-owned.

## Anti-Blur Rule 3
CEH Infrastructure Index must never be represented as identical to CEH Standard.

## Anti-Blur Rule 4
CEH Infrastructure Index must not be canonically buried inside CEH Standard without an explicit and approved domain strategy.

## Anti-Blur Rule 5
ORM must remain the top-level control and governance layer in all ecosystem maps.

## Anti-Blur Rule 6
Shared styles, shared components, or shared repos must not create implied shared ownership.

## Anti-Blur Rule 7
Execution-layer content must not overwrite or redefine standards-layer language.

## Anti-Blur Rule 8
Capital or investor materials must not be used as the de facto definition of ORM or CEH.

## Anti-Blur Rule 9
No public-facing property may obscure which entity the user is currently engaging with.

## Anti-Blur Rule 10
Repo structure, deployment topology, and domain structure must reinforce institutional hierarchy rather than contradict it.
